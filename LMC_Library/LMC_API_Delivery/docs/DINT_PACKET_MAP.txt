All numeric motion fields below are signed 32-bit little-endian LASAL internal DINT.
The API writes caller-provided DINT values directly to the packet.
Caller code must multiply the physical value by the selected LMC_Units constant,
round/check the DINT range, and pass the converted int to the motion API.
Read APIs return raw LASAL DINT; caller code divides by the same UNIT for display.

Malformed diagnostics requests keep the same 68-byte response shape and set
CommandStatus=1, ErrorId=-32000, and DetailCode to 1 UnsupportedSchema,
2 UnsupportedFeature, or 12 BoundsInvalid. DiagnosticsBootId=0 is legal only
while all stateful Bulk, Recorder, PI Write, SDO, and DigitalIOWrite capability
bits are zero.
A nonzero retained boot generation is required before any stateful D2-D5 or
DigitalIOWrite capability can be advertised.
RequestId zero is reserved and returns BoundsInvalid. If a malformed request
declares at least the complete 8-byte common envelope, the response still
echoes the received RequestId; a shorter request cannot provide an ID to echo.

- 0x7E23 SubmitDigitalOutputWrite: request 40, response ticket 32 bytes
  Request P8 TopologyRevision U32, P12 IOReference U32,
  P16 Value U64, P24 Mask U64, P32 ExpectedOutputRevision U32,
  P36 DiagnosticsBootId U32. Revision, IOReference, mask, output revision, and
  BootId are nonzero. Value bits outside Mask must be zero. The PLC RT owner
  must atomically reject a stale output revision or apply
  NewOutput=(OldOutput & ~Mask) | (Value & Mask). Whole-word write uses the
  complete advertised output valid mask. PC-side read-modify-write is forbidden.
  Executable SDK requests must be created with
  CreateDigitalOutputWriteRequest from a valid current-session Output snapshot.
  Detached raw requests, foreign/stale sessions, incomplete source capability
  provenance, or a changed BootId are rejected before command 0x7E23 is sent.
  Success returns OperationKind=DigitalOutputWrite(4) and reuses 0x7E03/0x7E04
  for status/cancel. The ticket exposes SubmissionTopologyRevision while its
  SubmissionMapRevision is zero.
  Terminal Success is acceptance of the RT-owner operation, not physical-output
  proof. The client must reread 0x7E22 for the same node/topology/IOReference and
  verify a nonzero changed OutputRevision, unchanged BitWidth/ValidMask, and the
  complete NewOutput value including preservation of every unmasked bit.
  Submission ambiguity, disconnect, or failed/mismatched readback must retain a
  mutation/Close interlock and must never trigger automatic replay. Explicit
  operator acknowledgement may clear only the client interlock after separate
  physical verification; it is not a VERIFIED write result.
  Submission exceptions retain their original type and expose a separate
  failure context: NotAttempted, explicit RPC/PLC Rejected, wire
  OutcomeUncertain, or Accepted with a ticket before post-submit session
  validation failed. Fake TCP tests cover sync/async Accepted, explicit RPC
  rejection, response-loss OutcomeUncertain, and the accepted-session race.

ReadRecorderBankInventory is a dormant, read-only Double-bank recovery contract
behind the same disabled gate. Its request is P8 DiagnosticsBootId U32,
P12 ConfigId U32, P16 MapRevision U32, P20 ConfigRevision U32, where zero
ConfigRevision discovers the exact current revision and a nonzero value requires
an exact match. Success keeps configuration identity visible even with zero
occupied banks: P16 DiagnosticsBootId, P20 ConfigId, P24 ConfigRevision,
P28 MapRevision, P32 configuration OwnerSessionEpoch, P36 configuration
ClosedSessionEpoch, P40 configuration State U16, P42 BufferMode U8,
P43 RecorderBufferCount U8, P44 OccupiedBankCount U8, P45..47 reserved zero.
Up to two compact occupied-bank entries begin at P48 with 20-byte stride:
RecordId U32, BufferId U32, OwnerSessionEpoch U32, ClosedSessionEpoch U32,
State U16, reserved U16. Entries are ordered by BufferId; unused entries are
all zero. The command never adopts, releases, or rewrites ownership. It rejects
mixed configuration/bank identity, mixed owner closure, active foreign owners,
non-Double configurations, and ambiguous bank states before returning metadata.
When the request carries a nonzero ConfigRevision, its BootId matches the
current diagnostics generation, its MapRevision matches the Recorder map, and
the complete Recorder store is canonically Empty (class identity/shape fields
zero, BufferReleased=true, and both bank descriptors and states empty), the PLC
returns the common error envelope with detail 32 RecorderConfigurationAbsent.
This is a read-only terminal absence proof for a persisted exact configuration
Release intent; it does not adopt, release, clear, or rewrite anything. The SDK
maps it to LMCRecorderConfigurationAbsentException bound to the requested
BootId/ConfigId/ConfigRevision/MapRevision. ConfigRevision=0 is never promoted
to this typed proof and remains fail-closed when no configuration exists.
Fault is deliberately outside the inventory/adoption recovery contract:
ReadRecorderBankInventory and AdoptRecorder reject a Fault bank, while
AdoptEmptyRecorderConfiguration accepts only exact Configured state. A Fault
record remains fail-closed for explicit manual recovery/reset and must not be
treated as empty, released, or safe to rebind.
AdoptEmptyRecorderConfiguration is a second dormant Double-bank recovery command
for the exact Configure-success/response-loss case where inventory reports zero
occupied banks. Its request is P8 DiagnosticsBootId U32, P12 ConfigId U32,
P16 ConfigRevision U32, P20 MapRevision U32, and P24 previous
OwnerSessionEpoch U32. All five identity values are required and exact. Success
requires Configured/Double/count-2 state, both physical banks Configured with
zero bank identity fields, the exact previous owner marked closed, and a distinct
nonzero caller session. It rebinds only the configuration OwnerSessionEpoch and
clears its ClosedSessionEpoch. It does not reset bank/data metadata or infer any
identity. The fixed response is P16 DiagnosticsBootId, P20 ConfigId,
P24 ConfigRevision, P28 MapRevision, P32 new OwnerSessionEpoch, P36 Configured
State U16, P38 Double BufferMode U8, and P39 RecorderBufferCount=2 U8. The SDK
returns a release-only recovered configuration lease; only exact 0x7E48 release
is defined for that type, and StartRecorder does not accept it. A lost 0x7E4B
success response is outcome-uncertain and is not retried in the same session:
the store does not retain a separate FromOwner proof after rebind. The client
faults/reconnects, reads 0x7E4A again after the attempted owner is closed, and
uses that newly returned exact previous owner for the next 0x7E4B request.
ConfigureRecoverableDoubleRecorder is the only Double Configure wire that may
be enabled with capability bit 6. Ordinary 0x7E40 keeps rejecting Double mode.
0x7E4C preserves the existing Configure fields at P8..P55, then carries an
opaque nonzero 128-bit recovery token at P56..P71 and SignalId[N] from P72.
RequestedConfigId must be nonzero. Success preserves the existing Configure
response at P0..P55 and echoes the exact token at P56..P71. The token, complete
configuration, and two Configured banks are committed before StateValue is
published. A token-qualified configuration cannot be overwritten by 0x7E40 or
a repeated 0x7E4C. Exact 0x7E48 Release clears the active token in the same
configuration-release generation and retains a per-boot last-token replay
fence; a late 0x7E4C using that token is rejected without changing ConfigId,
ConfigRevision, or NextConfigId.
ReadRecoverableRecorderBankInventory is the read-only recovery resolver for a
Configure response lost before ConfigRevision became durable on the client.
Its request is P8 DiagnosticsBootId U32, P12 requested ConfigId U32,
P16 MapRevision U32, and P20..P35 the exact token. Success uses the complete
0x7E4A inventory layout at P0..P87 and echoes the token at P88..P103. The client
persists the discovered nonzero ConfigRevision, then issues ordinary 0x7E4A
again before existing 0x7E4B/0x7E49 adoption and Release logic. If the current
BootId/map match and the complete Recorder store is canonically Empty with no
active token, detail 32 is promoted only on this command to
LMCRecoverableRecorderConfigurationAbsentException bound to the requested
BootId/ConfigId/map/token. That proof resolves only a v3 journal record marked
as ClientTokenV1. A legacy v2 ConfigRevision=0 record was never bound on wire and
remains zero-wire fail-closed. 0x7E4D never adopts, releases, changes ownership,
or repairs partial state; token mismatch, a live foreign owner, Fault, reboot,
or inconsistent bank/configuration metadata remains unresolved.
For a Mask trigger, TriggerValue is unused and must be zero; only the nonzero
TriggerMask participates in all-set/any-set/all-clear evaluation.
Automatic edge/window/mask evaluation requires MasterState=OP(8), zero consecutive
invalid cycles, and the trigger axis Online with ESMState=OP(8) and ALStatusCode=0.
An invalid cycle clears the previous-value history. A forced TriggerRecorder
request bypasses this input-health gate after the configured pre-history is ready.
StopRecorder publishes a stop sequence. When RT observes it, the store freezes
before copying that cycle's sample. A non-empty record retains EndCycle and
EndTimestamp from its last copied sample; Stop does not append an extra sample.

D4 active TriggerRecorder 0x7E42:
Request payload is exactly 28 bytes and uses the Recorder identity layout above.
Success response is common-only 16 bytes. Current PLC capability bit 5 is one.
The PLC validates identity/owner/map/BootId/state and publishes a forced-trigger
sequence to the RT recorder. Manual configurations and inactive records reject it.
TriggerRecorder and StopRecorder success ACKs mean that their request sequence was
published, not that RT already applied it. If a request races a natural terminal
transition, the final ReadRecorderStatus StopReason and TriggerIndex are authoritative.
Ring upload remaps wrapped physical samples to chronological offset order.
Recorder header DataCrcPolicy is None, DataCrcPresent is clear, and every Recorder
chunk DataCRC32 is zero. DroppedSamples/DroppedCycles and OverflowCount are reserved
and currently always zero; zero is not PLC runtime proof of no loss.
Before a trigger, Ring recording can update its bounded pre-history indefinitely.
Exact reconnect recovery keeps the saved BootId/RecordId/BufferId and calls
AdoptRecorder. If Start response loss or an app crash loses RecordId, the client
first verifies the nonzero BootId and calls AdoptActiveRecorder, which sends
RecordId=0 and BufferId=0 on the same 0x7E49 wire command. The PLC discovers the
one current closed-owner bank and returns its actual identity. Mixed zero/nonzero
identity is rejected. This discovery contract is single-bank only; Double-bank
capability remains off.
The SDK validates exact pre/trigger/post shape only for a locally configured
identity: TriggerIndex=PreTriggerSamples and TriggerComplete SampleCount equals
PreTriggerSamples+1+PostTriggerSamples. AdoptRecorder does not return that shape,
so adopted identities are checked only against common frozen wire invariants.

D5 GetOperationStatus 0x7E03 and CancelOperation 0x7E04:
Request payload is exactly 16 bytes:
P8 TicketId U32, P12 DiagnosticsBootId U32.
The general-inline test profile validates ticket, BootId and owner session. Status
returns the fixed 64-byte operation envelope and its P24 SubmitCycle must exactly
match the QueuedCycle captured in the accepted ticket. Cancel succeeds only for the
owning Queued ticket; Running and terminal tickets return InvalidState.
Malformed sizes return BoundsInvalid. A gate-off build returns UnsupportedFeature.

D5 SubmitSDO 0x7E50 request header is 32 bytes plus write data:
P8 MapRevision U32, P12 SlaveReference U16, P14 OperationFlags U16,
P16 ObjectIndex U16, P18 SubIndex U8, P19 ValueType U8,
P20 TimeoutCycles U32, P24 DataLength U16, P26 reserved,
P28 DiagnosticsBootId U32, P32 WriteData[]. The current test profile sets bit 8
SDORead and bit 13 SDOReadGeneralInline; bit 9 SDOWrite is zero.
The parser accepts only OperationFlags 0/1, reserved=0, an exact 32-byte read
request, or an exact 32+DataLength-byte write request. The active general-inline
profile allows only OperationFlags=0, slave 1..4, nonzero ObjectIndex, any U8
SubIndex and TimeoutCycles=1..60000. DataLength must exactly match ValueType:
Bool/Int8/UInt8/BitField8=1, Int16/UInt16/BitField16=2, and
Int32/UInt32/Real32/BitField32=4. It returns a Queued operation ticket. A
successful terminal status carries exactly 1, 2 or 4 inline bytes and all unused
result-tail bytes are zero. 8/12-byte reads and result chunks remain fail-closed;
malformed shapes return BoundsInvalid or CapacityExceeded.

The prepared Write path accepts only OperationFlags=1, an exact 36-byte request,
ValueType=Int32(4), DataLength=4 and four little-endian data bytes. When the PLC
global gate and the matching per-axis gate are enabled and every policy/state
check passes, the returned ticket uses OperationKind=SDOWrite(3); successful
terminal status has ResultLength=0 and
zero result data. The only prepared candidate is Gold UI[24] at 0x2F00:24 on one
of slaves 1..4, with the conservative local range -1073741823..1073741823. It is
not approved yet: LMC_DIAG_D5_SDO_WRITE_GLOBAL_ENABLED and all four
LMC_DIAG_D5_SDO_WRITE_UI24_AXIS1_ENABLED..AXIS4_ENABLED gates are FALSE until the
user drive program proves UI[24] unused and one target axis is selected. The
deployment rule is to enable only that selected axis gate. The matching C#
SdoWriteEnabled/SdoWriteUi24Axis1Enabled..Axis4Enabled gates and allowlist are
also closed/empty, so the GUI remains disabled and raw Write requests are denied
by policy. Arbitrary
SDO writes are not supported. DS402 direct motion/control objects 0x6040, 0x607A,
0x60FF and 0x6071 are permanently UnsafeWriteBlocked. PI Write 0x7E21 and extended
result 0x7E51 remain disabled.

The executor publishes Running before StartReadSDO or StartWriteSDO can callback.
It copies Write data into executor-owned storage before dispatch. It owns cleanup
through a private Releasing state, returns an owned validation failure as a
terminal ticket result, and releases a late orphan callback back to Idle. An
unsolicited/duplicate callback or impossible compare-exchange transition remains
hard Quarantined. Submit reports InternalError detail 24 when no public ticket or
drain owns a non-Idle executor; ResourceBusy detail 9 is reserved for an owned
queued/running/draining operation.

The SDO Write source/API/WPF infrastructure and PC tests are not LASAL IDE build,

0x204A GroupPowerOn, payload 1 byte (project-local LASAL extension; absent from the

0x204B GroupPowerOff, payload 1 byte (project-local LASAL extension; absent from the

[8] Execute BYTE = 1
The handler starts asynchronous LMCRobot.RobotOff processing. A success ACK means

The current client completion contract sends each 0x204A or 0x204B request exactly
once, then WaitForPowerStateAsync polls only 0x2045 until three consecutive
successful samples match the expected IsPowerOn value. Resuming pending
verification sends status reads only and never replays the original power command.
One manual GroupReadStatus cannot by itself complete pending power or Enable
verification or promote unverified ACTIVE/profile-lock readiness. A successful
response published against the current safety generation does, however, accumulate
in the matching pending GroupEnable continuation proof. At 3/3 Locked Standby proof,
Resume can complete by reusing the accepted ACK without replaying 0x2047. A
Stop/PowerOff safety reservation
resets that proof to zero while preserving the accepted ACK and continuation. A
response arriving after the reservation is drained and discarded as ResultDiscarded
without being observed. Recovery-required is entered only in the narrow race where
SDK completion publication finished before the reservation but WPF had not applied
that completion yet. While connected and unresolved, group-name mutation, group
reload, clean connection/window close, connected reconnect, and a new PowerOn are
blocked. After an external connection loss, reconnect entry promotes the state to
recovery for the retained exact group name, and only that group may be reloaded in
the new session. A successful explicit 0x2048 GroupDisable ACK means only that
UnlockProfile was accepted; it does not release pending or recovery-required state.
Both states are released only after three consecutive powered Disabled/Unlocked
samples or three consecutive PowerOn=False samples for the retained exact group. A successful
PowerOn alone does not release either state, and no path replays 0x2047. This is
deterministic PC/fake-TCP evidence, not PLC runtime proof.

Before a fresh 0x2047 dispatch, the WPF writes a separate durable recovery record
containing endpoint IPv4/port, group name/reference, DiagnosticsBootId, and
MapRevision. An ArmedBeforeDispatch record found at startup is promoted to
RecoveryRequired. Endpoint mismatch is rejected before TCP/RPC; BootId/MapRevision
and group-reference mismatches allow only the required read-only identity checks and
send no group mutation. Verified Enable, explicit Disable, or verified PowerOff
resolves the durable record before volatile state is cleared, after a final identity
and safety-generation check. No recovery path automatically replays 0x2047.

0x2047 GroupEnable / ProfileLock, payload 1 byte
[8] Execute BYTE = 1
The handler calls LMCRobot.LockProfile for the validated static mapping. A success
ACK means the lock request was accepted. The standard Maestro
NC_GROUP_STANDBY_MASK (0x00020000) identifies standby; this adapter sets it for
the locked standby condition exposed as IsStandby/IsEnabled.
The earlier live capture exposed a handler defect: after LockProfile returned
_LMCPROF_NoError, the handler read LockState in the same CyWork call and could return
ErrorId -6 before the asynchronous state update. The tracked LASAL source now ACKs
native acceptance and verifies final lock only through 0x2045 polling; SourceOnly and
full static contracts pass. A new LASAL IDE build/download and live acceptance capture
are still required. Clients must never convert a native nonzero error to success.

0x2048 GroupDisable / ProfileUnlock, payload 1 byte
[8] Execute BYTE = 1
The handler requires ProfileInPosition(_LMCPROF_ProfileFinished), then calls
LMCRobot.UnlockProfile. A moving or unverified profile is rejected with -6.
A success ACK means the unlock request was accepted; it is not completion. The
handler does not read LockState again in the same CyWork call. Clients prove final
completion only through 0x2045 polling. BeginGroupDisableWaitForStableDisabledAsync
sends 0x2048 once, while same-session Resume and cross-session
WaitForStableDisabledAsync send only 0x2045 until three consecutive successful
samples show PowerOn + Disabled + !Standby. A newer stable PowerOff may retire the
pending Disable as superseded, but it must not be reported as Disable completion.
The standard Maestro
NC_GROUP_DISABLED_MASK (0x00010000) identifies disabled; this adapter sets it for
the unlocked disabled condition exposed as IsDisabled.

Response payloads implemented by command-specific parsers:
- AxisInfo: 8 bytes, handle/reserved[0], status UINT16[4], error INT16[6]
- Axis ReadStatus: 12 bytes, state UDINT[0], status UINT16[4], error INT16[6],
  axis error UINT16[8], status word UINT16[10]
  The canonical LASAL server writes the native _LMCAXIS_STATUS bitfield to
  state[0]. PowerOn is bit 0 (0x00000001) and Standstill is bit 25
  (0x02000000). Do not apply the legacy PMAS 0x80/0x200 readiness masks.
  StatusWord[10] is reserved and currently always 0; DS402 StatusWord is not
  connected to this response yet.
- Axis ReadActualPosition: 8 bytes, position DINT[0], status UINT16[4],
  error INT16[6]
- Group ReadStatus: 12 bytes, state UDINT[0], status UINT16[4], error INT16[6],
  group error UINT16[8], padding UINT16[10]
  0x00040000 is the project-local LASAL Power Ready extension (IsPowerOn).
  0x00020000 is the standard Maestro NC_GROUP_STANDBY_MASK and 0x00010000 is
  NC_GROUP_DISABLED_MASK. The project-local part is the adapter condition that
  maps locked standby to IsStandby/IsEnabled and unlocked disabled to IsDisabled.
- GetGroupMembersInfo: exactly 1350 bytes; see RESPONSE_MODEL_DESIGN_2026-07-09.md
- Group ReadActualPosition: exactly 68 bytes, position DINT[16] at [0..63],
  status UINT16[64], error INT16[66]. The current source copies Pos1..Pos9 and
  zero-fills slots 10..16; the intended 4-vs-9 public read contract is pending
  PLC verification. Legacy 136-byte LREAL is rejected.

- UDP callback payload remains raw because no event datagram capture/contract exists.

- Multi-PC read sharing and motion/control ownership must be enforced by the LASAL
